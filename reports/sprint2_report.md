### 4.1 รายละเอียดผลการทดสอบ "กด Interact รัวๆ" (เพิ่มเติม 30/9/69)

**วิธีทดสอบ:** รันเซิร์ฟเวอร์ Flask ของโปรเจกต์จริง (ค่าเริ่มต้นเดียวกับที่ `app.py` ใช้ตอนรันจริง คือ `threaded=False`)
แล้วยิง HTTP request ไปที่ `/api/interact` แบบ "พร้อมกันจริง" 30 request ด้วย thread pool (ไม่ใช่กดทีละครั้งแบบ manual)
โดย mock เฉพาะการเรียก Dog API/Cat Facts API ภายนอก (เพราะสภาพแวดล้อมที่ใช้ทดสอบไม่มีอินเทอร์เน็ตออกไปหาโดเมนภายนอกได้
เหมือนปัญหาที่เจอตอน Sprint 2 เดิม ดูหัวข้อ 3) ส่วน logic การอ่าน/เขียนไฟล์ประวัติ (`web/history.py`) เป็นของจริงทั้งหมด ไม่ได้ mock

**ผลลัพธ์:**

| ขั้นตอน | ผล |
|---|---|
| จำนวนประวัติก่อนทดสอบ | 22 รายการ |
| ยิง request พร้อมกัน | 30 request → ได้ HTTP 200 ครบทั้ง 30 |
| จำนวนประวัติหลังทดสอบ | 52 รายการ (22 + 30 ตรงตามที่คาดหวังเป๊ะ) |
| สรุป | **ไม่มีรายการตกหล่น ไม่มีรายการซ้ำ — PASSED** |

**ข้อสังเกตเชิงเทคนิคที่ควรบันทึกไว้อย่างตรงไปตรงมา:** ผลทดสอบผ่าน แต่ความปลอดภัยนี้ในปัจจุบัน "ปลอดภัยเพราะบังเอิญ"
มากกว่า "ปลอดภัยเพราะออกแบบไว้โดยตั้งใจ" กล่าวคือ `add_entry()` ใน `web/history.py` เขียนไฟล์แบบอ่าน-แก้-เขียนทับทั้งไฟล์
(read-modify-write) โดยไม่มีการล็อกไฟล์ (file locking) เลย ที่ทดสอบแล้วไม่พังเพราะ Flask dev server ที่ใช้รันโปรเจกต์นี้
(`app.run(debug=True, port=5000)`) มีค่าเริ่มต้นเป็น `threaded=False` ทำให้ request ถูกประมวลผล "เรียงทีละอัน" อยู่แล้ว
โดยธรรมชาติ ไม่ได้ประมวลผลพร้อมกันจริงในระดับไฟล์ ถ้าในอนาคตเปลี่ยนไปรันด้วย server ที่รองรับ concurrency จริง
(เช่น deploy ด้วย gunicorn หลาย worker) จะต้องเพิ่ม file locking ใน `add_entry()` ก่อน ไม่เช่นนั้นมีโอกาสเกิด
race condition ของไฟล์ประวัติได้จริง

**สรุป:** ข้อนี้ทดสอบแล้วอย่างละเอียดตามที่ตั้งใจไว้ ผลผ่าน (ไม่ตกหล่น/ไม่ซ้ำ) แต่บันทึกเหตุผลเชิงเทคนิคไว้ตามความเป็นจริง
ว่าทำไมถึงปลอดภัยในสภาพแวดล้อมปัจจุบัน เพื่อไม่ให้ดูเหมือนอ้างว่าโค้ดออกแบบให้ปลอดภัยจาก race condition โดยสมบูรณ์

### 4.2 อัปเดตหลังทดสอบบนเครื่องจริง (30/9/69) — พบบั๊กจริงและแก้ไขแล้ว

ผลทดสอบในหัวข้อ 4.1 ข้างบนทำในเครื่อง sandbox ด้วยการ mock API ภายนอก ซึ่งดูผ่าน แต่พอทดสอบ
ซ้ำแบบเดียวกันบนเครื่องจริงของทีม (ผ่าน Chrome DevTools Console ยิง 30 request จริงพร้อมกันด้วย
`Promise.all` + `fetch`) กลับพบว่า **ถึงแม้ HTTP ตอบ 200 ครบ 30 ครั้ง แต่ประวัติที่บันทึกจริงกลับหายไป
ทั้งหมด (ของเก่าที่มีอยู่ก่อนก็หายไปด้วย)** โดยพบบรรทัดนี้ในเทอร์มินัลฝั่งเซิร์ฟเวอร์ตอนเกิดเหตุ:

```
[warn] อ่านไฟล์ประวัติไม่สำเร็จ (Extra data: line 141 column 3 (char 4897)) จะเริ่มประวัติใหม่
```

**สาเหตุที่แท้จริง:** มี 2 request ที่เข้ามาพร้อมกันจริง (เบราว์เซอร์เปิดหลาย connection พร้อมกันในระดับ
เครือข่ายจริง) เขียนทับไฟล์ `data/interaction_history.json` ชนกันพอดี ทำให้ไฟล์ JSON เพี้ยน (มีข้อมูล
2 ชุดถูกเขียนต่อกันแบบไม่ถูกไวยากรณ์) แล้วโค้ดเดิมใน `load_history()` ที่เจอไฟล์เพี้ยนจะ "เริ่มประวัติใหม่"
แบบเงียบๆ (คืนค่า list ว่างโดยไม่แจ้งเตือนผู้ใช้) ทำให้ของเก่าทั้งหมดหายไปในพริบตา — เป็น race condition
จริงที่เกิดขึ้นได้แม้รันเซิร์ฟเวอร์ตัวเดียว (`threaded=False`) เพราะการชนกันเกิดที่ระดับไฟล์ ไม่ใช่ที่ระดับ
เธรดของเซิร์ฟเวอร์

**วิธีแก้ที่ทำจริง** (แก้ใน `web/history.py`):
1. เพิ่ม file lock (`_FileLock` เขียนเองแบบไม่พึ่งไลบรารีภายนอก ใช้ `os.open(..., O_CREAT | O_EXCL)`
   ซึ่ง atomic ทั้งบน Windows/Linux) ครอบทั้งขั้นตอนอ่าน-แก้-เขียนใน `add_entry()` กันไม่ให้ 2 request
   เข้าถึงไฟล์พร้อมกัน
2. เปลี่ยน `save_history()` ให้เขียนไฟล์แบบ atomic (เขียนลงไฟล์ชั่วคราวก่อนแล้วค่อย `os.replace()`
   ทับไฟล์จริง) กันไฟล์เพี้ยนแม้โดนขัดจังหวะกลางคัน

**ผลหลังแก้ (ทดสอบซ้ำบนเครื่องจริงแบบเดียวกันเป๊ะ):** ยิง 30 request พร้อมกันอีกครั้ง ได้ 200 ครบ 30
ประวัติเพิ่มขึ้นครบ 30 รายการจริง (จาก 26 เป็น 56) ไม่มีของเก่าหาย ไม่มีรายการซ้ำ และไม่มี warning ขึ้นใน
เทอร์มินัลอีกเลย (`pytest` ยัง 87 passed, `flake8` ยังผ่าน เหมือนเดิม ไม่กระทบโค้ดส่วนอื่น)

**สรุป:** checklist ข้อนี้เดิมทดสอบแบบ mock ในเครื่อง sandbox แล้วดูผ่าน แต่พอทดสอบจริงบนเครื่องจริง
กลับเจอบั๊กจริง จึงแก้โค้ดจริงแล้วทดสอบซ้ำจนมั่นใจว่าปลอดภัยจริง ไม่ใช่ "ผ่านเพราะบังเอิญ" แบบที่บันทึกไว้
ในหัวข้อ 4.1 อีกต่อไป

## 6. ผลการประเมินตนเอง (Self-Assessment)
> **ตัวอย่างการกรอก** (หนูลองกรอกให้ดูเป็นแนวทาง) — ทีมควรอ่านแล้วปรับคะแนน/เหตุผลให้ตรงกับความเป็นจริง

| หัวข้อประเมิน | ดีเยี่ยม (4) | ดี (3) | กำลังพัฒนา (2) | ไม่ผ่าน (1-0) |
